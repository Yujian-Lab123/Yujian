《遇见》项目总说明与 MVP 开发计划
0. 你的角色

你现在是本项目的：

高级产品工程师 + 全栈开发者 + AI/RAG 工程师 + 推荐系统工程师。

请实际完成项目，而不是只给方案。

项目暂定名称：

遇见

一句话定位：

发现一个值得聊一句的人。

核心概念：

知乎已经帮助用户找到值得看的内容；
「遇见」希望让 AI 再往前一步，通过用户长期留下的真实内容，帮助用户发现一个原本不会认识、但可能值得聊一句的人。

本项目首先用于知乎 Hackathon Demo。

当前目标不是开发一个完整成熟的社交网络，而是验证一个核心假设：

AI 是否能够通过两个人长期留下的内容 + 此刻状态 + 当前连接意愿，发现一个双方真正愿意进一步了解的人？

一、产品背景

知乎用户长期留下了大量：

回答
文章
想法
收藏
关注
评论
人生经历
专业观点
对具体问题的选择与思考

传统推荐系统主要利用这些数据回答：

用户接下来可能想看什么？

「遇见」希望尝试另外一个问题：

这些内容背后的人，是否存在值得被彼此发现的潜在关系？

传统社交软件通常首先展示：

照片
性别
年龄
学校
工作
兴趣标签

然后让用户判断：

要不要认识这个人？

「遇见」采用相反的顺序：

内容
↓
产生共鸣
↓
进一步了解
↓
发现作者
↓
产生“想认识这个人”的兴趣
↓
双向同意
↓
建立连接

核心原则：

先理解一个人的思想，再认识这个人。

但需要注意：

“先内容后人”本身并不是创新，小红书、Slowly 等产品已经存在类似机制。

「遇见」真正需要验证的创新点是：

AI 能否通过一个人的长期内容历史，主动发现传统内容推荐系统不会发现的人际连接。

二、产品核心模型

不要简单把用户理解成一个 Embedding。

每个用户至少需要包含四个层级。

1. Long-term Self：长期自我

来自用户长期知乎内容。

用于理解相对稳定的：

长期兴趣
长期关注主题
专业领域
反复出现的问题
明确表达过的价值选择
人生阶段
内容表达方式
真实经历

例如：

长期主题：
AI / 软件 / 投资 / 阅读

反复问题：
自由与稳定
长期选择
职业意义

明确表达：
更重视自主选择
愿意长期投入感兴趣的事情

这一层以月、年为时间尺度。

不需要频繁重新计算。

2. Present Self：此刻自我

来自：

今日心情
最近状态
「侧面」内容
最近想聊的问题
最近发生的事情

例如：

最近项目很多，有些疲惫
最近想找个人晚上散步
正在纠结毕业城市
最近很想认识一些新朋友

这一层是短周期信号。

可以设置：

24小时
7天
30天

随着时间自动降低权重。

3. Intent：当前连接意愿

这个必须由用户明确选择。

不要让 AI 猜。

例如：

遇见开关：ON

希望认识：
朋友
恋爱可能
同行
合作伙伴
户外搭子
随便聊聊

以及可选硬条件：

年龄范围
城市
性别偏好
是否接受异地
人生阶段

第一版不要要求用户配置太多。

默认可以只有：

愿意认识新朋友。

4. Content Anchors：认识一个人的内容入口

一个用户可能有 100 篇甚至更多内容。

不能把所有内容每次重新交给 LLM。

系统第一次处理用户时，需要识别：

哪几篇内容最能够代表 TA 的不同侧面？

例如：

职业选择代表内容
个人生活代表内容
长期价值思考代表内容
兴趣代表内容
人生经历代表内容

建议每个用户保留：

3～10 个 Content Anchors。

每个 Anchor 保存：

原始 URL
标题
摘要
主题
内容 Embedding
与用户长期画像之间的关系

以后 A 匹配到 B 时，系统继续做：

B 的哪一篇内容最适合先展示给 A？

这叫：

Content Bridge
三、不要建立“人格测试”

本项目使用：

Content Profile

不要宣传成：

人格画像。

系统只能根据用户实际授权内容总结：

TA写过什么、经常讨论什么、明确表达过什么。

必须区分：

explicit
原文明确表达

inferred
AI根据多篇内容归纳

unknown
无法确定

不要未经支持输出：

MBTI
依恋类型
精神状态诊断
智商
人格障碍
“灵魂伴侣”
伪精确心理概率

也不要用：

灵魂契合度 93%

作为核心 UI。

四、产品真正匹配的不是“相似度”

系统需要优化的核心应该叫：

Conversation Potential

即：

两个人之间是否存在值得开始一次对话的东西？

因此需要同时考虑：

长期内容是否存在交集
长期关注的问题是否类似
双方有没有值得讨论的差异
人生阶段是否有一定相关性
当前状态是否存在交集
当前是否愿意认识人
现实条件是否允许
是否具有新颖性
是否已经曝光过

不是：

越像越好

完全一样的人不一定最值得认识。

适度差异有时反而更容易产生：

“我想问问 TA 为什么这么想。”

十、LLM Deep Match

只有 Top 5～10 才交给 Qwen3.8-Max 等较强模型。

LLM需要判断：

A 为什么可能想认识 B？
B 为什么可能想认识 A？
有没有真正的 Conversation Potential？
有没有只是“主题相似”但实际没什么可聊？
双方最重要的共同点是什么？
哪个差异反而值得讨论？

最终选择：

Top 1～3
十一、匹配必须考虑双向

不能只算：

A → B

还要估计：

B → A

例如：

A → B = 90
B → A = 42

不应该成为优先推荐。

而：

A → B = 82
B → A = 79

更加值得。

可以使用：

MutualScore = min(A→B, B→A)

第一版足够。

也可以以后尝试：

sqrt(A→B × B→A)
十二、Content Bridge

匹配出 B 后：

不要直接告诉 A：

给你推荐 B。

系统需要继续从 B 的 Content Anchors 中选择：

哪一篇内容最适合先给 A 看？

例如 B 是摄影创作者。

文章有：

《如何选择35mm镜头》

《我为什么最后没有去大厂》

《一次西藏旅行》

《如何调色》

A长期关心：

职业选择、自由、长期规划。

系统应该优先展示：

《我为什么最后没有去大厂》

而不是摄影教程。

因为这一篇是：

A认识B最自然的入口。

这就是产品非常重要的：

Content Bridge
十三、Conversation Bridge

AI接着根据双方真实内容生成：

一个两个人真的可能聊得下去的问题。

例如：

A长期写：

工作稳定性。

B长期写：

自由职业。

那么：

如果收入下降30%，但是每周多两天完全属于自己的时间，你会接受吗？

比：

“你好，你也喜欢科技吗？”

高级很多。

AI不要代替用户发送消息。

只负责：

找到一个值得开始的地方。

五十六、比赛 Pitch 核心表达

推荐：

知乎已经帮助我们找到值得看的内容。

但每一篇内容背后，还有一个人。

你偶然刷到他的回答，
偶然点进主页，

所以我们做了：

五十八、工程原则

开发过程中必须遵守：

1. 优先让核心路径能跑

不要过度工程。

2. 先 Mock，再接真实 API

不要因为 OAuth 卡住导致整个产品没有 Demo。

3. 所有外部 API 做 Adapter

例如：

ZhihuProvider
LLMProvider
EmbeddingProvider
RerankProvider

方便替换。

4. 所有 AI 输出使用 Schema Validation

不要直接相信自由 JSON。

推荐：

Zod / Pydantic
5. AI失败必须有 fallback

推荐结果不能因为某次模型 JSON 错误就整个页面崩掉。

6. API Key只放服务器。
7. 保留日志

至少记录：

模型
token
latency
错误
prompt version

方便黑客松快速调试。

最终产品原则

始终记住：

我们不是在开发一个新的 Tinder。

也不是：

给两个人计算一个神秘匹配分。

我们想探索的是：

AI 能不能从一个人长期留下的内容中，发现一个他原本不会遇见的人；再用一篇内容和一个问题，让两个人产生一次自然、低压力、值得继续的交流。

如果一个功能不能明显帮助这件事情：

第一版不要做。
